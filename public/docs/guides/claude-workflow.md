## なぜ準備が大切か

Claude Code は優秀ですが、**「何を作るか」が曖昧なまま投げると意図と違うものが生成されます**。指示が不明確なほど、Claude は「それっぽいもの」で補完するからです。

よくある失敗パターン：

- 「SNS アプリ作って」→ フォロー・いいね・DM が全部出てくるが、自分が想定していた小さなアプリと全然違う
- 「認証を追加して」→ どんな認証方式か、セッション管理はどうするかを決めていないまま実装が進む
- 途中で仕様変更 → 変更のたびに大きなリファクタリングが発生する

**1時間の準備が、10時間の手戻りを防ぎます。**

## 開発前に決める5つのこと

### 1. ユーザーは誰か

「誰のために作るか」が決まると、UI の複雑さ・機能のスコープが自然に絞られます。

> 「エンジニアが1人で使う管理ツール」と「非エンジニアが毎日使う SaaS」では、作るものが全く違う

チェックリスト：
- メインのユーザーは自分か、他人か
- テクニカルなユーザーか、一般ユーザーか
- デバイスは PC メインか、スマホメインか

### 2. 解決する課題

機能を列挙する前に、**「何が不便か」を1文で書く**。これが軸になります。

例：
- ❌ 「タスク管理アプリ」（何を解決するか不明）
- ✅ 「毎朝 Notion を開くのが面倒で、CLI から素早くタスクを追加したい」

### 3. 機能一覧（MVPスコープ）

MVP（最小実用版）に絞ることが重要です。Claude は頼んだものを全部作ろうとするので、スコープを明示しないと過剰な実装になります。

テーブル形式で整理すると Claude に渡しやすいです：

| 機能 | MVP | 将来 |
|------|-----|------|
| ユーザー登録・ログイン | ✅ | — |
| タスク CRUD | ✅ | — |
| タグ付け | — | ✅ |
| チーム共有 | — | ✅ |

### 4. 技術スタック

スタックを明示しないと、Claude が知っている「よくある構成」で実装されます。自分の環境に合わせて指定しましょう。

```
- フレームワーク: Next.js 16 (App Router)
- 言語: TypeScript
- DB: Neon (Serverless Postgres)
- 認証: iron-session
- スタイリング: Tailwind CSS v4
- デプロイ: Vercel
```

### 5. スコープ外（やらないこと）

「やること」と同じくらい「やらないこと」が重要です。明示しないと Claude が自主的に追加します。

例：
- 管理者画面は作らない
- メール送信機能は MVP に含めない
- 多言語対応は対象外

## 仕様書テンプレート

以下をコピーして CLAUDE.md または仕様ドキュメントとして使ってください。

```markdown
# [プロジェクト名] 仕様書

## 概要
[1〜2文で何を作るかを説明]

## ユーザー
[誰が使うか、どんな場面で使うか]

## 解決する課題
[何が不便で、どう解決するか]

## 技術スタック
- フレームワーク: 
- DB: 
- 認証: 
- デプロイ: 

## MVP 機能
- [ ] 機能1
- [ ] 機能2
- [ ] 機能3

## スコープ外
- 機能A は含めない
- 機能B は将来対応

## ディレクトリ構成
[主要なファイル・フォルダの説明]

## 注意事項
[守ってほしいコーディングスタイル・制約など]
```

## Claude への効果的な投げ方

### CLAUDE.md を使う

リポジトリのルートに `CLAUDE.md` を置くと、Claude Code は毎回自動で読み込みます。プロジェクト固有のルール・スタック・注意事項を書いておくと一貫した実装になります。

```markdown
# CLAUDE.md

## スタック
Next.js 16 App Router, TypeScript, Tailwind CSS v4, Neon Postgres

## ルール
- コメントは原則書かない（自明なコードに限り）
- Server Component をデフォルトにし、必要な場合のみ 'use client'
- CSS は CSS Variables を使う（Tailwind の arbitrary value より優先）
- エラーハンドリングは境界でのみ行う
```

### タスクを小さく分割する

「認証機能を全部作って」ではなく、1ステップずつ頼むのがコツです。

```
❌ 「ログイン・サインアップ・パスワードリセットを全部実装して」

✅ ステップ1: 「DB に users テーブルを作るマイグレーション SQL を書いて」
   ステップ2: 「/api/auth/signup の POST ルートを実装して」
   ステップ3: 「/login ページのフォームコンポーネントを作って」
```

### コンテキストを渡す

関連ファイルを開いた状態で頼むか、ファイルパスを明示します。

```
「lib/users.ts の findUserByEmail を使って、
 app/api/auth/login/route.ts にログイン API を実装して」
```

### 確認しながら進める

実装後に必ず動作確認してから次のステップへ。問題があれば同じコンテキストのまま修正を頼めます。

## よくある失敗パターン

**1. 仕様変更を後から言う**
実装が進んだ後に「やっぱりこの機能も欲しい」は大きなリファクタリングを招きます。MVP スコープを事前に固めることが最も重要です。

**2. 一度に多くを頼みすぎる**
Claude は長い指示ほど重要度が薄まります。1リクエスト = 1機能 が基本です。

**3. エラーをそのまま貼り付ける**
エラーメッセージだけでなく、「どの操作をしたら出たか」「関連ファイルはどれか」を添えると解決が速いです。

**4. レビューをスキップする**
Claude が生成したコードは動くが最適でないことがあります。特に DB クエリ・認証・バリデーション周りは必ず自分でレビューしてください。

**5. CLAUDE.md を更新しない**
スタックや制約が変わったら CLAUDE.md も更新します。古い情報があると Claude が矛盾した実装をすることがあります。

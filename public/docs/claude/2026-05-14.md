## 🆕 今週の注目トピック

### MCP（Model Context Protocol）が個人開発の武器になる

MCP は Claude Code が外部ツール・API・DB と通信するための標準プロトコル。「Claude が自分で調べて、自分で操作する」を実現する基盤。

現時点で公式・コミュニティ製の MCP サーバーが多数公開されており、設定ファイルに追記するだけで即使える。

**すぐ使える MCP サーバー例:**

| サーバー | できること |
|----------|-----------|
| `@modelcontextprotocol/server-filesystem` | ローカルファイルの読み書き |
| `@modelcontextprotocol/server-github` | PR・Issue・コードの操作 |
| `@modelcontextprotocol/server-postgres` | DB へのクエリ実行 |
| `@modelcontextprotocol/server-brave-search` | Web 検索 |

**設定例（`.claude/settings.json`）:**

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxx" }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb"]
    }
  }
}
```

設定後は「GitHub の Issue #42 を読んで修正して PR を作って」が一発で動く。

### Hooks システムで CI を自前で組む

Claude Code の Hooks は「ツール実行の前後にシェルスクリプトを挟む」機能。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "pnpm lint --fix" }
        ]
      }
    ]
  }
}
```

ファイルを書き込むたびに自動で `lint --fix` が走る。「書いたらすぐ壊れる」を防げる。

## ⚡ 開発効率を上げる実践Tips

### 1. 拡張思考（Extended Thinking）を使う場面を絞る

Claude に難しい判断をさせる前に「じっくり考えてから答えて」と伝えると精度が上がる。ただしトークンを多く使うため、使い所を絞るのが重要。

**向いている場面:**
- 複数ファイルをまたぐアーキテクチャ変更
- バグの根本原因調査（スタックトレースが複雑なもの）
- セキュリティ上のトレードオフ判断

**向いていない場面:**
- 型定義の追加、定型コードの生成
- ファイル名の変更・移動
- コメントの修正

```
// 拡張思考を促すプロンプト例
「このバグを修正する前に、関連するすべてのファイルを読み込んで
原因の仮説を3つ立て、それぞれの検証方法を説明してください。
その後で最も確度の高い修正を実装してください」
```

### 2. CLAUDE.md に「してはいけないこと」を書く

「やること」より「やってはいけないこと」を書く方が効果的。Claude はデフォルトで親切にいろいろやろうとするため、制約で絞り込む。

```markdown
## 禁止事項

- テストを書かずに実装を完了と報告しない
- `any` 型を使わない
- `TODO:` コメントを残したまま PR を作らない
- 既存のコンポーネントを削除する前に確認を取る
- npm/yarn ではなく pnpm を使う（lockfile が pnpm 形式のため）
```

### 3. `/checkpoint` で作業の節目を記録する

長いセッションの途中で `/checkpoint` を打つと、それまでの変更履歴をサマリー化してくれる。「何を変えたか」を後から追いやすい。特に大きなリファクタリングの途中で有効。

### 4. サブエージェントに「役割」を与える

並列タスクを割り振るとき、役割を明示すると出力の質が上がる。

```
「以下を並列で実行してください:
1. セキュリティレビュアーとして: 認証周りのコードを調べ、脆弱性を報告
2. パフォーマンスエンジニアとして: DB クエリの N+1 問題を探す
3. テストエンジニアとして: カバレッジが低いファイルをリストアップ」
```

### 5. エラーは「状況ごと」貼る

エラーだけ貼るより「どの操作をしたときに出たか」を添えると診断が速い。

```
// ❌ エラーだけ
「TypeError: Cannot read properties of null (reading 'id')」

// ✅ 状況付き
「ログイン済みユーザーがダッシュボードにアクセスすると
以下のエラーが出ます。ゲストユーザーは正常。

TypeError: Cannot read properties of null (reading 'id')
  at Dashboard (app/dashboard/page.tsx:23:18)」
```

### 6. `git stash` を Claude に任せない

Claude は積極的に `git stash` を使うことがある。スタッシュされた変更は見落としやすいため、CLAUDE.md に制約を書いておくと安全。

```markdown
## Git ルール

- `git stash` は使わない。作業途中のファイルはそのまま残す
- コミット前に必ず `git diff` を表示して確認を取る
- force push は絶対に行わない
```

## 🛠 個人開発者向け おすすめワークフロー

### MCP を使ったフルスタック開発フロー

```
1. GitHub MCP でタスクを取得
   「Issue #12 の内容を読んで、実装に必要なファイルをリストアップして」

2. Postgres MCP でスキーマを確認
   「現在の users テーブルの定義を確認して、必要なマイグレーションを提案して」

3. 実装
   「Issue の要件に従って実装してください。型は既存のパターンに合わせて」

4. Filesystem MCP でテストを確認
   「テストファイルのパターンを確認して、同じスタイルでテストを追加して」

5. GitHub MCP で PR 作成
   「実装が完了したので PR を作成してください。Issue #12 と紐づけて」
```

### コスト節約：モデルを段階的に使うフロー

```bash
# 1. Haiku で素早くドラフト
claude --model haiku-4-5 "この API のレスポンス型を TypeScript で定義して"

# 2. Sonnet で実装（デフォルト）
# → 日常の実装はこれで十分

# 3. Opus は週1〜2回の設計判断のみ
claude --model opus-4-7 "この認証フローに設計上の問題がないか、セキュリティの観点でレビューして"
```

## 💡 モデル使い分けガイド（週1回更新）

| モデル | 主な用途 | 向かないケース | コスト感 |
|--------|----------|---------------|---------|
| Opus 4.7 | 複雑な設計・セキュリティ監査・難解なバグ調査 | 定型作業・高頻度タスク | 高（慎重に使う） |
| Sonnet 4.6 | 日常コーディング・PR レビュー・ドキュメント | 超単純なタスク | 中（メインモデル） |
| Haiku 4.5 | データ変換・定型処理・大量バッチ | 複雑な判断が必要なもの | 低（気軽に使える） |

### 今週のコスト最適化ポイント

MCP を使い始めると Claude がファイルを大量に読み込むためトークン消費が増える。対策：

- `CLAUDE.md` に「必要なファイルだけ読む。全ファイルを無差別にスキャンしない」と明示
- `/compact` を早めに使う（コンテキストが半分を超えたタイミングが目安）
- Opus は「設計の相談」のみ。「実装」は必ず Sonnet か Haiku で

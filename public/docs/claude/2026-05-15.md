## 🆕 今週の注目トピック

### Claude Code の `/ultrareview` — マルチエージェントによるコードレビュー

`/ultrareview` は現在のブランチ（またはGitHub PR番号）を複数のエージェントが並列でレビューする機能。単一のエージェントによるレビューと比べて、見落としが減る。

```bash
# ローカルブランチをレビュー
/ultrareview

# GitHub PR をレビュー
/ultrareview 42
```

実行すると以下の観点から独立して調査される:
- セキュリティ（OWASP 系の脆弱性、認証ロジックの穴）
- パフォーマンス（N+1、不要な再レンダリング）
- テストカバレッジの欠落
- アーキテクチャの一貫性

> **注意:** 課金が発生する操作のため、`/ultrareview` はユーザーが明示的に起動する必要がある。自動実行はできない。

### GitHub Actions × Claude Code の自動レビューフロー

PR が開かれたタイミングで Claude Code がコードレビューコメントを自動投稿するワークフローが組める。

```yaml
# .github/workflows/claude-review.yml
name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          claude --print "このPRの変更をレビューして、問題点をGitHubコメント形式でまとめて"
```

> 実際のワークフロー構成は公式ドキュメントを参照。上記はイメージ。

## ⚡ 開発効率を上げる実践Tips

### 1. TDD（テスト駆動開発）を Claude に任せる

Claude はテストを先に書かせると実装の品質が上がる。先にテストを書いてもらい、その後で実装を依頼するフローが効果的。

```
// ❌ 実装から頼む（テストが後付けになりがち）
「ユーザー認証の API を実装してください」

// ✅ テストから頼む
「ユーザー認証 API のテストを先に書いてください。
以下のケースをカバーしてください:
- 正常なログイン
- 間違ったパスワード（401）
- 存在しないメール（401）
- セッション切れ後のリクエスト（401）
テストが通るように API を実装してください」
```

テストが先にあると、Claude は「テストを壊さないように」実装する。結果としてエッジケースの考慮が増える。

### 2. `CLAUDE.md` にテスト方針を書く

テストの書き方をプロジェクトごとに統一するには `CLAUDE.md` に明記するのが最速。

```markdown
## テスト方針

- テストランナー: Vitest
- テストファイルの場所: `__tests__/` ディレクトリ
- モック方針: DB は絶対にモックしない。テスト用 DB に接続する
- 命名: `describe('関数名')` → `it('〜のとき〜を返す')` 形式
- 1テストにつき1アサーション（複数確認が必要なら分割）
- カバレッジ目標: lib/ 配下は 90% 以上

## 禁止

- `any` 型でテストを回避しない
- `@ts-ignore` を使わない
- `setTimeout` でフレーキーなタイミング問題を回避しない
```

### 3. スナップショットテストより振る舞いテスト

Claude にスナップショットテストを書かせると、変更のたびに大量の更新が発生する。振る舞い（behavior）を検証するテストを指定する。

```typescript
// ❌ スナップショット（壊れやすい）
expect(component).toMatchSnapshot()

// ✅ 振る舞いを検証
expect(screen.getByRole('button', { name: 'ログイン' })).toBeInTheDocument()
expect(screen.getByText('メールアドレスを入力してください')).toBeVisible()
```

Claude に「スナップショットテストは使わない。ユーザーの操作と結果を検証するテストを書いて」と伝えるだけで品質が変わる。

### 4. エラーシナリオを先にテストする

正常系より先にエラー系のテストを書かせると、防御的な実装になりやすい。

```
「以下のエラーシナリオのテストを先に書いてください:
- ネットワークタイムアウト
- 不正な JSON レスポンス
- 認証トークンの期限切れ
- DB 接続の失敗
それぞれで UI が適切なエラーメッセージを表示することを検証してください」
```

### 5. テスト名を日本語で書く

Claude に日本語でテスト名を書かせると、後から読んだときに意図が伝わりやすい。英語の命名規則に縛られず、要件を自然言語で表現できる。

```typescript
describe('isSubscribed', () => {
  it('サブスク期限が未来の場合は true を返す', () => {
    const future = new Date(Date.now() + 1000 * 60 * 60 * 24)
    expect(isSubscribed(future)).toBe(true)
  })

  it('サブスク期限が過去の場合は false を返す', () => {
    const past = new Date(Date.now() - 1000)
    expect(isSubscribed(past)).toBe(false)
  })

  it('null の場合は false を返す（無料ユーザー）', () => {
    expect(isSubscribed(null)).toBe(false)
  })
})
```

### 6. カバレッジレポートを Claude に読ませる

`vitest --coverage` の出力を貼り付けて「カバレッジが低いファイルのテストを追加してください」と頼むと、漏れを素早く補える。

```bash
# カバレッジ付きで実行
pnpm vitest run --coverage

# レポートを Claude に貼る
# 「カバレッジが 80% を下回っているファイルのテストを追加してください」
```

### Claude × Vitest の TDD サイクル

実際に試せる TDD フロー。新機能を追加するときに使う。

```
ステップ1: 要件をテストで表現する

「次の機能のテストを書いてください（実装は後でします）:
- 関数名: formatSubscribedUntil
- 引数: Date | null
- null の場合: '無料プラン' を返す
- 未来の日付の場合: '2026年6月14日まで有効' 形式の文字列を返す
- 過去の日付の場合: 'サブスク期限切れ' を返す」


ステップ2: テストが落ちることを確認

pnpm vitest run __tests__/lib/format.test.ts
# → 全テスト FAIL（関数がまだないので当然）


ステップ3: テストを通す実装を書かせる

「上のテストが全て通るように formatSubscribedUntil を実装してください」


ステップ4: テストを通す

pnpm vitest run __tests__/lib/format.test.ts
# → 全テスト PASS


ステップ5: リファクタリング

「実装を読みやすくリファクタリングしてください。テストは変更しないでください」
```

### CI でテスト + 型チェックを自動化する

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v2
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - name: 型チェック
        run: pnpm tsc --noEmit

      - name: テスト
        run: pnpm test

      - name: ビルド確認
        run: pnpm build
```

Claude に「このリポジトリに CI を追加してください」と頼むと、`package.json` のスクリプトを読んで自動でワークフローを生成してくれる。

## 💡 モデル使い分けガイド（週1回更新）

| モデル | 主な用途 | 向かないケース | コスト感 |
|--------|----------|---------------|---------|
| Opus 4.7 | 複雑な設計・セキュリティ監査・大規模リファクタリング計画 | 定型作業・高頻度タスク | 高（週1〜2回の判断のみ） |
| Sonnet 4.6 | 日常コーディング・テスト作成・PR レビュー | 超単純なタスク | 中（メインモデル） |
| Haiku 4.5 | 定型コード生成・データ変換・大量バッチ処理 | 複雑な判断が必要なもの | 低（気軽に使える） |

### テスト作成のモデル選択

| タスク | 推奨モデル | 理由 |
|--------|-----------|------|
| 新規モジュールのテスト設計 | Sonnet 4.6 | 設計判断が必要。Haiku では抜けが出る |
| 既存関数の追加テスト | Haiku 4.5 | パターンが明確。コスト効率が良い |
| E2E テストのシナリオ設計 | Opus 4.7 | ユーザーフロー全体の考慮が必要 |
| テストのリファクタリング | Sonnet 4.6 | コードを読んで整理する能力が必要 |

### 今週のコスト最適化ポイント

テスト作成はパターンが繰り返されるため、Haiku で十分なケースが多い。

```bash
# テスト追加は Haiku でコスト削減
claude --model haiku-4-5 "この関数のテストを __tests__/ に追加して"

# 設計相談は Sonnet
claude "このテスト構造を見て、改善点を教えて"

# アーキテクチャ判断のみ Opus
claude --model opus-4-7 "このシステムのテスト戦略を設計してください"
```

## 🆕 今週の注目トピック

### Claude Code SDK の Agent ループ改善

Claude Code SDK（`@anthropic-ai/claude-code`）の Agent ループが安定化され、サブエージェントの並列実行でのコンテキスト汚染が減少した。特に複数ファイルを同時編集するタスクで、互いの変更が干渉しにくくなっている。

**実際に試す:**

```bash
# サブエージェントに並列でタスクを渡す例（CLAUDE.md から呼び出し）
claude -p "フロントエンドのバグを調査して" &
claude -p "バックエンドのテストを修正して" &
wait
```

並列実行は独立したタスクにのみ使う。共有ファイルへの書き込みが重なる場合は順次実行を選ぶ。

### Hooks による自動化の強化

`settings.json` の hooks 機能で「コマンド実行後に自動でフォーマットをかける」「コミット前に型チェックを走らせる」といった自動化が設定できる。CI との二重チェックを避けつつ、ローカルでの品質維持に有効。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx tsc --noEmit 2>&1 | head -20" }
        ]
      }
    ]
  }
}
```

## ⚡ 開発効率を上げる実践Tips

### Tip 1: CLAUDE.md の「禁止事項」セクションを先に書く

Claude Code は肯定的な指示より「やってはいけないこと」を明示した方が一貫性が高い。

```markdown
## やってはいけないこと

- `console.log` デバッグを残したままコミットしない
- `any` 型を使わない（やむを得ない場合はコメントで理由を書く）
- 既存のテストを削除しない
- `git push --force` を main/master に使わない
```

こういったリストがあるだけで、長いタスクでも逸脱が減る。

### Tip 2: ファイルの読み込み順をコントロールする

Claude Code はプロンプトに渡す前にファイルを読むが、どのファイルを先に読むかを `@ファイル名` で明示的に指定できる。

```
@lib/types.ts @lib/db.ts を先に読んだ上で、
api/users/route.ts のバリデーションを追加して
```

型定義と DB スキーマを先に渡すと、型ミスが大幅に減る。

### Tip 3: エラーは全文コピーして貼り付ける

「エラーが出る」ではなく、ターミナル出力をそのまま貼る。スタックトレースの3行目に原因が書いてあることが多い。Claude Code はエラー全文から根本原因を特定するのが得意。

```
以下のエラーが出ています:

Error: Cannot find module '@/lib/db'
    at Function.Module._resolveFilename (node:internal/modules/cjs/loader:1039:15)
    at Function.Module._load (node:internal/modules/cjs/loader:885:27)
    ...

tsconfig.json の paths 設定を確認して修正してほしい
```

### Tip 4: 「差分だけ見せて」を使いこなす

長いファイルを全部書き直してもらうより、「変更点だけ教えて」と聞く方が速い。特に 200 行超のファイルは有効。

```
上記の変更で何行目の何を変えるか、diff 形式で教えて
```

その後 `Edit` ツールで実際の変更を適用してもらう流れが効率的。

### Tip 5: サブエージェントに「報告書」を返させる

複雑な調査タスクをサブエージェントに渡すとき、返答フォーマットを指定しておくと後続処理が楽になる。

```
以下の形式で報告してください:

## 調査結果
- 問題のある箇所: [ファイル名:行番号]
- 根本原因: 
- 推奨修正:
```

## 🛠 今日試すべきワークフロー

### Next.js App Router プロジェクトを Claude Code で効率的に開発する

**ステップ 1: プロジェクト構造を先に理解させる**

```
このリポジトリの全体像を把握してほしい。
特に以下を確認して:
- app/ 以下のルーティング構造
- lib/ の主要ユーティリティ
- 使っている DB / 認証ライブラリ
```

**ステップ 2: 型定義ファイルを渡す**

```
@lib/types.ts @lib/db.ts @lib/session.ts

上記の型定義を踏まえて、以下の API ルートを実装して:
POST /api/items — ログイン済みユーザーが新しいアイテムを作成する
```

**ステップ 3: テストを先に書かせる**

```
実装の前に、このエンドポイントのテストケースを列挙して。
- 正常系: 
- 異常系:
- 境界値:
```

テストリストが揃ってから実装に入ると、実装漏れが減る。

**ステップ 4: 段階的に実装する**

```
まず DB のクエリ部分だけ実装して。UI はまだ触らなくていい。
```

1タスク1変更に絞ると、問題が起きたときに原因を特定しやすい。

**ステップ 5: レビューを依頼する**

```
今実装した api/items/route.ts について:
- セキュリティ上の問題はないか
- エラーハンドリングに漏れはないか
- パフォーマンス上の懸念はないか
```

## 💡 モデル使い分けガイド（週1回更新）

| モデル | 主な用途 | コスト感 | 使うべき場面 |
|--------|----------|----------|------------|
| Claude Opus 4.7 | 複雑な設計・リファクタリング・アーキテクチャ判断 | 高 | 1回あたり時間をかける大きなタスク |
| Claude Sonnet 4.6 | 日常的なコーディング・バグ修正・説明 | 中 | コーディングセッションのメイン |
| Claude Haiku 4.5 | 単純な変換・フォーマット・短い質問 | 低 | 大量の軽作業・自動化パイプライン |

**実践的な使い分け:**

- 「このファイルの関数名をスネークケースに変えて」→ Haiku
- 「このバグを直して」→ Sonnet
- 「このシステム全体のアーキテクチャを見直して」→ Opus
- 「このコードのセキュリティレビューをして」→ Opus

**コスト最適化のコツ:**

```bash
# CLAUDE.md にデフォルトモデルを書いておく
# 重いタスクだけ明示的に Opus を指定する
claude --model claude-opus-4-7 "システム全体のリファクタリング計画を立てて"
```

Claude Code はデフォルトで Sonnet を使う。重いタスクのときだけ `--model` を指定するのが費用対効果が高い。

## 📊 よく使うコマンドリファレンス

```bash
# セッション継続（コンテキストを維持したまま再接続）
claude --continue

# 特定のファイルをコンテキストに含めて起動
claude @src/components/MyComponent.tsx "このコンポーネントをリファクタリングして"

# モデルを指定して実行
claude --model claude-opus-4-7 "..."

# 非インタラクティブモード（CI / スクリプトから呼ぶ）
claude -p "テストを実行して失敗したものをリストアップして" --output-format json

# MCP サーバーを指定して起動
claude --mcp-config mcp-servers.json
```

**環境変数でよく使うもの:**

```bash
# APIキー（~/.zshrc に書いておく）
export ANTHROPIC_API_KEY="sk-ant-..."

# デフォルトモデルの指定
export CLAUDE_MODEL="claude-sonnet-4-6"

# ログレベル（デバッグ時）
export CLAUDE_DEBUG=1
```
